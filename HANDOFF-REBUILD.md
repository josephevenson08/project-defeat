# Part 1 — where the project is now

## What it is today

A **local-first React + TypeScript + Vite** planner/simulator for WoW TBC Classic Anniversary,
targeting game Phase 2 (Serpentshrine Cavern + Tempest Keep, Tier 5). No backend, no database, no
network calls at runtime — everything is typed data in the repo, rendered in the browser.

Verify you are where this describes:

```bash
npx tsc -b                            # clean
npm run lint                          # exit 0
npm run build
npx playwright test --reporter=line   # 60 passing. Use --reporter=line, not the default.
npm run brain                         # "all wikilinks resolve"
npm run brain                         # "0 written" — idempotent; repo lives in OneDrive, churn matters
```

`git status` should be clean apart from an untracked `Untitled.canvas`, which is the user's own file —
leave it. (`Untitled 1.canvas` **is** tracked and is a 2-byte OneDrive sync artefact; probably wants
removing, but confirm first.)

## Repo conventions that encode real, repeated mistakes

- `domain/` never imports from `features/` or `components/`. The only architectural invariant.
- **Never ship a module nothing renders.** This repo has done it three times (raids panel,
  `buildSerialization`, a half-wired import).
- Any value not read off a real source gets `needsVerification: true`. Confident recall is not a source.
- `src/styles/global.css` is **CRLF**. Append with CRLF or the diff shows the whole file changed.
- When `npx tsc -b` flags an unused import, find out what it was for before deleting it. That is how
  half-finished work gets discovered here.
- **Gate commits on the actual test exit code.** `npm test | tail` followed by `&& git commit` commits
  even when the suite fails, because the pipe's exit status is the tail's. A red commit was pushed this
  way once.
- `.claude/agents/` is **not registered as agent types in every environment**. Dispatching
  `sim-verifier` or `tbc-researcher` may fail with "agent type not found". Workaround that works:
  dispatch a `general-purpose` agent and paste the contents of `.claude/agents/<name>.md` into the
  prompt verbatim. Also tell it to append findings to a scratchpad file **as it goes** — agents on this
  repo have died mid-run four times (session limits, API errors) and incremental saving is the only
  reason that work survived.

## What works

All 9 classes and 27 specs, faction-aware race legality, the full TBC gear slot model, spec-aware slot
visibility and weapon/relic legality, gear/gems/enchants/buffs/consumables/target debuffs,
raids/bosses/attunements, professions, saved build slots with export/import, and a generated Obsidian
vault under `brain/` (`npm run brain`) that maps modules and imports and fails on broken wikilinks.

## The single most important thing to know about the data

**48 catalogue items have been audited against real Wowhead tooltips across six batches. Every single
one was wrong.** Not randomly — the catalogue was generated by *inferring what an item should look
like* for its role and slot. That is why it is uniformly plausible and consistently wrong:

- Stats invented that the item does not carry — dodge and parry on five separate tank pieces, a Spirit,
  base spell hit, crit ratings, `mp5` on three healer trinkets that have none.
- **Sockets wrong in both directions.** Chest pieces uniformly given `['Red','Yellow','Blue']`; seven of
  eight tier gauntlets have *zero* sockets and were each given a pair anyway; the one item that
  genuinely has sockets had none listed. Sockets can never be inferred, only looked up.
- Item level as a flat placeholder — every shoulder read 128 against a real 133.
- Two healer legs at different item levels carrying the **identical** wrong `healingPower: 58`.
- Whole-category errors: two Voidheart pieces are Tier 4 not Tier 5; one item typed plate is leather.

**Plausibility is not evidence in this dataset.** This is the main argument for replacing it rather
than repairing it — see Part 3, decision 4.

Two specific traps: a `"fictional placeholder item"` note appears on several entries and has been
**wrong on all six checked** — every one was a real item. Conversely `shield-of-rehearsal` could not be
found in Wowhead's TBC database at all by two independent searches.

## The largest gap in the current product

**BiS lists are one item deep.** Nearly every slot offers a single option while the panel labels it
"1 ranked" — presenting one guess as a considered ranking. Every spec *can* fill every slot the UI
offers (no dead ends; there is a test), but 17 slots have exactly one option, clustered in tank and
healer specs.

## Decisions already made, worth not re-arguing

Full versions in `brain/Project/Decision Log.md` (generated, versioned in `tools/brain/generate-brain.mjs`).

**Three ways to answer a systematic gap — the pattern generalises better than the fixes:**

- **Derive it** — armor was recorded on 5 of ~143 armour pieces. TBC armor is deterministic given item
  level, armour class, slot and quality, so one formula fixed 58 items.
- **Surface it** — of sixteen Tier 5 set bonuses, not one is a flat stat addition. Listed and marked
  unscored rather than invented into stats.
- **Decline it** — the Feral cat rotation needs a time-stepped loop; this engine is closed-form, so it
  was not built at all.

Others: tank survivability is **Effective Health**; item procs are averaged by uptime
(`duration / cooldown`) or declined where the value is not a stat bonus; **counts are computed, never
written down**.

## Known-wrong or missing

Healer HPS has **no mana constraint**. **Meta gem activation requirements are never checked.** Tier set
data covers 5 of 9 classes. Weapon and armour procs are unpopulated (schema exists, data does not).
`src/data/phase2Enhancements.ts` and `phase2SpecGuides.ts` are ~1460 lines imported by nothing. Glove
and boot enchants exist for one role each. Rotations cover 2 specs of 27. Gems (11) and enchants (22)
are thin.

# Part 3 — decisions (settled 2026-08-06)

## 1. No MongoDB yet — stay local-first

**Decided: skip Mongo for now, revisit later.**

The client keeps working against typed data / a generated JSON bundle in the repo, so the app stays
fast, offline and deployable as static files. When MERN does come back, the intended shape is
**Mongo + Express as the authoring and ingestion side** that *produces* that bundle — not a runtime
dependency the UI cannot render without. That gets the stack onto the project without making a gear
planner require a server to show a gear list.

Practical consequence: nothing in the rebuild should assume an API exists. Build data access behind a
thin module so swapping a static import for a fetch later is a one-file change.

## 2. Design direction

**Decided: Discord's skeleton, Tesla's palette and restraint, Nothing's detailing. Mixed light and
dark, mostly dark.**

- **Layout — Discord.** Persistent left rail, main content pane, popups over modes. The left rail is
  where the WoWSims-style stat readout lives, since that is the part the user specifically called out
  as wanting.
- **Palette and spacing — Tesla.** Restrained, generous whitespace, large clean type, very few
  elements competing per screen. Mostly dark surfaces with lighter panels or sections where contrast
  helps — not a single flat tone, and not a light app.
- **Detailing — Nothing.** Flat surfaces, hairline rules instead of shadows and rounded cards, tracked
  uppercase mono labels, tabular figures for numbers, no gradients.

## 3. Colour policy

**Decided: item quality colour stays. Everything decorative goes. Other colour is allowed but must not
draw the eye.**

Quality colour is how a player reads gear at a glance, so it is information, not decoration. The rest
of the interface stays near-monochrome *specifically so quality reads first*. Where colour is needed
for meaning — a gain, a warning, an unverified flag — keep it muted rather than saturated.

The current build already went this way and it is worth keeping: the previous purple/pink gradients and
a magenta-to-violet button fill were the loudest things on screen and competed directly with the only
colours that mean anything.

## 4. Catalogue: replace, don't repair — my call, per delegation

**Decided: bulk-ingest a real item dataset and keep the already-sourced items as an override layer.**

Reasoning, since this was delegated on "best, fastest, most reliable":

- **Repairing is not viable at this scale.** Every one of 48 audited items was wrong. At ~8 items per
  research batch and ~124 still flagged, that is ~15 more rounds *just to reach the current 230* — and
  the goal is now every item across every class's BiS guide, which is far more than 230.
- **The guide pages are the wrong ingestion route.** Wowhead guide pages are JavaScript-rendered and a
  plain fetch returns a shell. They are good for *rankings*, bad for bulk item data.
- **Best source: the wowsims TBC item database.** `github.com/wowsims/tbc` carries a structured,
  complete TBC item dataset with stats, sockets, item level and quality. This session already used that
  repo successfully as a primary source for combat constants and the defender-side attack table, and
  its numbers held up every time they were checked. Bulk, structured, and already validated by a
  community that sims against it.
- **Validate, don't trust blindly.** Spot-check an ingested sample against Wowhead `item=<id>&xml`
  tooltips, which have been reliable all session. Check the wowsims licence before vendoring data.
- **Keep the ~106 sourced items as overrides.** They were read off real tooltips and should win over
  bulk data on conflict — and any conflict is a useful signal about the bulk source's quality.

Wowhead's BiS guides then supply **rankings**, layered on top of the ingested catalogue. That also
fixes the "463 entries, 2 ranked deeper than one" problem, which is the largest gap in the current
product.

## 5. Simulator: hide, don't delete

**Decided: hide from the UI, keep the code.**

`src/domain/simulation/` and `src/features/simulator/` hold the most carefully sourced work in the
project — the attack tables, the defender-side avoidance research, Effective Health, the armor
derivation formula. Deleting it throws away research that took real effort to get right.

**Consequence to plan for:** stat weights and the upgrade finder are *built on* the simulation, so
hiding it takes those with it. The left-rail stat readout becomes **plain stat totals**, not weighted
values. The armor derivation should stay wired into stat calculation regardless, since armor is a
displayed stat rather than a simulation-only one.

  few specs or do all up front? Not yet decided.
- **Scale of the item import.** Hundreds or thousands of items? Affects whether a static bundle stays

  green suite during the rebuild as meaningful until they are re-pointed.

## Suggested order of operations

1. **Catalogue ingestion first.** Everything data-shaped depends on it, and it is the long pole.
2. **One screen mocked** in the new design language before building the rest, to settle the
   dark/light balance in practice rather than in prose.
3. **Gear panel + gem/enchant popup** against the new catalogue.
4. **BiS rankings** layered on top, with real depth per slot.
5. **Consumables and raid buffs** per spec.
6. **Simulator last**, unhidden and re-pointed once the rest is stable.
