# Part 1 — where the project is now

## What it is today

A **local-first React + TypeScript + Vite** planner/simulator for WoW TBC Classic Anniversary,
targeting game Phase 2 (Serpentshrine Cavern + Tempest Keep, Tier 5). No backend, no database,
no network calls at runtime — everything is typed data in the repo, rendered in the browser.

Verify you are where this describes:

```bash
npx tsc -b                            # clean
npm run lint                          # exit 0
npm run build
npx playwright test --reporter=line   # 60 passing. Use --reporter=line, not the default.
npm run brain                         # "all wikilinks resolve"
npm run brain                         # "0 written" — idempotent; repo lives in OneDrive, churn matters
```

`git status` should be clean apart from an untracked `Untitled.canvas`, which is the user's own file.
Leave it. (Note `Untitled 1.canvas` **is** tracked in git and is a 2-byte OneDrive sync artefact —
probably wants removing, but confirm first.)

## Repo conventions that encode real, repeated mistakes

- `domain/` never imports from `features/` or `components/`. The only architectural invariant.
- **Never ship a module nothing renders.** This repo has done it three times (raids panel,
  `buildSerialization`, a half-wired import).
- Any value not read off a real source gets `needsVerification: true`. Confident recall is not a
  source.
- `src/styles/global.css` is **CRLF**. Append with CRLF or the diff shows the whole file changed.
- When `npx tsc -b` flags an unused import, find out what it was for before deleting it. That is how
  half-finished work gets discovered here.
- `.claude/agents/` is **not registered as agent types in every environment**. Dispatching
  `sim-verifier` or `tbc-researcher` may fail with "agent type not found". Workaround that works:
  dispatch a `general-purpose` agent and paste the contents of `.claude/agents/<name>.md` into the
  prompt verbatim. Also tell it to append findings to a scratchpad file **as it goes** — agents on
  this repo have died mid-run three times and incremental saving is the only reason the work survived.

## What works

- All 9 classes, 27 specs, faction-aware race legality, full TBC gear slot model.
- Spec-aware slot visibility and weapon/relic legality rules.
- Gear, gems, enchants, buffs, consumables, target debuffs, raids/bosses/attunements, professions.
- Saved build slots, export/import.
- A simulator: real TBC attack and spell tables, rating conversions, armor mitigation, stat weights,
  and a per-slot upgrade finder.
- A generated Obsidian vault under `brain/` (`npm run brain`) that maps modules, imports and domain
  data. Fails on broken wikilinks. Idempotent.

## The single most important thing to know about the data

**48 catalogue items have been audited against real Wowhead tooltips across six batches. Every single
one was wrong.** Not randomly — the catalogue was generated by *inferring what an item should look
like* for its role and slot. That is why it is uniformly plausible and consistently wrong:

- Stats invented that the item does not carry — dodge and parry on five separate tank pieces, a
  Spirit, base spell hit, crit ratings, `mp5` on three healer trinkets that have none.
- **Sockets wrong in both directions.** Chest pieces uniformly given `['Red','Yellow','Blue']`; seven
  of eight tier gauntlets have *zero* sockets and were each given a pair anyway; the one item that
  genuinely has sockets had none listed. Sockets can never be inferred, only looked up.
- Item level as a flat placeholder — every shoulder read 128 against a real 133.
- Two healer legs at different item levels carrying the **identical** wrong `healingPower: 58`.
- Whole-category errors: two Voidheart pieces are Tier 4 not Tier 5; one item typed plate is leather.

**Plausibility is not evidence in this dataset.** Treat any unaudited entry as wrong until checked.

Two specific traps: a `"fictional placeholder item"` note appears on several entries and has been
**wrong on all six checked** — every one was a real item. Conversely `shield-of-rehearsal` could not
be found in Wowhead's TBC database at all by two independent searches.

## The largest gap in the current product

**BiS lists are one item deep.** 463 entries across 27 specs, 2 ranked deeper than one. Nearly every
slot offers a single option while the panel labels it "1 ranked" — presenting one guess as a
considered ranking. Bigger than the verification backlog, and it is the core promise of a planner.

Every spec *can* fill every slot the UI offers it (no dead ends — there is a test), but 17 slots have
exactly one option, clustered in tank and healer specs.

## Decisions already made, worth not re-arguing

Full versions in `brain/Project/Decision Log.md` (generated, versioned in
`tools/brain/generate-brain.mjs`).

**Three ways to answer a systematic gap, and the pattern generalises better than the fixes:**

- **Derive it** — armor was recorded on 5 of ~143 armour pieces. TBC armor is deterministic given item
  level, armour class, slot and quality, so one formula fixed 58 items. Legitimate *because* the value
  genuinely is a function of known things; that had to be established before building.
- **Surface it** — of sixteen Tier 5 set bonuses, not one is a flat stat addition. They attach to named
  abilities, resource costs, or the party. Listed and marked unscored rather than invented into stats.
- **Decline it** — the Feral cat rotation needs a time-stepped loop tracking energy ticks and combo
  points. This engine is closed-form and never advances a clock, so it was not built at all.

Others: tank survivability is **Effective Health** (health ÷ fraction of a swing that lands), which
replaced a composite whose weights were invented. Raw damage-taken-per-second was rejected partly for a
structural reason — `score` is consumed by stat weights and the upgrade finder, both assuming
higher-is-better, so a lower-is-better headline would have broken both for one role. Item procs are
averaged by uptime (`duration / cooldown`) or declined outright where the value is not a stat bonus.

## Known-wrong or missing, as of now

- Healer HPS has **no mana constraint** — an unbounded ceiling, not a sustainable rate. `mp5` is
  computed and displayed but never caps anything.
- **Meta gem activation requirements are never checked.** Every meta gem's stats apply unconditionally.
- Tier set data covers 5 of 9 classes. Rogue, Priest, Warlock and Shaman get nothing surfaced.
- Weapon and armour procs are unpopulated — the schema exists, the data does not. Heartrazor's +270 AP
  proc is prose only.
- `src/data/phase2Enhancements.ts` and `phase2SpecGuides.ts` — ~1460 lines, imported by nothing.
- Glove and boot enchants exist for one role each; every other role has zero options in those slots.
- Rotations cover 2 specs of 27 (Fury and Arms Warrior).
- Gems (11) and enchants (22) are thin.

# Part 3 — questions to resolve before building

The user explicitly asked to be questioned rather than have an interpretation assumed. These are the
ones where guessing wrong wastes the most work.

## 1. MERN — what is the database actually for?

This is the biggest question and it changes everything else. The project today is deliberately
**local-first with no backend**; that is a recorded architectural decision, and it is what makes it
work offline and deploy as static files.

MongoDB + Express + Node means a server, a database, and a deployment story. Worth establishing which
of these is the goal:

- **The item catalogue lives in Mongo** rather than in typed TS files? That solves the "all items from
  every BiS guide" problem (thousands of items are unwieldy as source files) but means the app needs a
  running API to show anything.
- **User accounts and saved builds server-side**, so builds sync across devices or can be shared by
  link?
- **Learning/CV goal** — MERN is the stack you want on the project regardless of whether the app needs
  it?

All three are legitimate; they imply very different amounts of work. A middle path worth considering:
keep the client working against a static generated JSON bundle, and have Mongo/Express be the
*authoring and ingestion* side that produces it — you get the stack, the app stays fast and offline.

## 2. Three design references that pull in different directions

- **Discord** — dense, dark, persistent left rail, app chrome, information-heavy.
- **Tesla** — spacious, light, big type, generous whitespace, marketing layout, very few elements per
  screen.
- **Nothing** — monochrome, flat, hairline rules, dot-matrix/mono type, near-zero colour.

Discord and Tesla are close to opposites on density. Best guess at what is wanted: **Discord's layout
skeleton** (left rail + main pane), **Tesla's palette and restraint** (near-white or near-black,
generous spacing, big clean type), **Nothing's detailing** (hairlines, mono labels, no gradients).
Worth confirming — and specifically:

- **Light or dark?** Tesla is light. Discord is dark. WoW item quality colours read far better on dark.
- **Do item quality colours survive?** "Colors should be like Tesla's rather than having colorful
  options" could mean *no colour anywhere*, or *no decorative colour, but quality colours stay because
  they carry meaning*. Purple/blue/green on item names is how every WoW player reads gear at a glance;
  losing it would hurt usability. Strong recommendation: keep quality colour, kill everything else.

## 3. "All items from the BiS guides" — how do we get them?

The linked page is an index of per-class BiS guides. Getting every item from every tier list means
tens of guides, and Wowhead's guide pages are **JavaScript-rendered** — a plain fetch returns a shell.
Some options:

- Wowhead's `item=<id>&xml` endpoint returns real tooltips reliably and has been the workhorse for all
  sourcing so far — but it needs item **IDs**, which the guide pages are what provide.
- Item *listing* pages (e.g. `/tbc/items/armor/plate/slot:5`) render server-side and expose name, item
  level and stats as plain columns. That may be a better ingestion route than the guides.
- How many items are we talking about — hundreds, or a few thousand?

Also worth a decision: does the existing 230-item catalogue get **repaired** or **replaced**? Given
every audited item so far has been wrong, replacing it wholesale from a real source is probably
cheaper than 15 more verification batches — but it throws away the sourced work already done on ~106
items. Those could be preserved as an override layer.

## 4. "Drop the simulation feature"

Does that mean:

- **Hide it from the UI** but keep `src/domain/simulation/` and `src/features/simulator/` intact for
  later, or
- **Delete it**?

Recommendation: hide, don't delete. That code is where the most carefully sourced work in the project
lives — the attack tables, the defender-side avoidance research, Effective Health, the armor
derivation. Deleting it loses research that took real effort to get right. But note that stat weights
and the upgrade finder are *built on* the simulation, so dropping it means those go too, and the left
rail of stats becomes a pure stat total rather than anything weighted.

## 5. Consumables and raid buffs per class/spec

The linked page is one spec's consumables guide. Doing this for all 27 specs is 27 guide pages. Worth
confirming: is per-spec consumable/buff data wanted for **all** specs up front, or start with a few
and expand?

## 6. What happens to the existing tests?

There are 60 Playwright tests, many of which encode real findings — that Feral cat form swings its own
weapon, that a both-weapons special halves its off-hand, that avoidance pushes crushing blows off the
attack table. A full UI replacement invalidates every UI-driven assertion but **not** the pure-data
ones. Recommendation: keep the domain tests, expect to rewrite the UI ones, and do not treat a green
suite during the rebuild as meaningful until they are re-pointed.

## Suggested order of operations

1. **Settle question 1 (MERN scope) first.** It determines whether this is a reskin or a re-platform.
2. Settle the design direction (question 2) with a single screen mocked before building the rest.
3. Decide catalogue repair vs replace (question 3). This is the long pole and everything data-shaped
   depends on it.
4. Build the gear panel + gem/enchant popup against whatever the catalogue becomes.
5. Consumables and buffs per spec.
6. Revisit simulation last, with the domain code preserved rather than deleted.
